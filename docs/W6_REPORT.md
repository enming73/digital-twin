# W6 implementation report — in progress, not accepted

> Status note (2026-11-10): the durable-source recovery work in [`W6_RECOVERY_REPORT.md`](W6_RECOVERY_REPORT.md) supersedes the MQTT-only burst failure for the recovery path. This report's acceptance table describes the state before that work.

## Current implementation

The optional `compose.w6.yml` adds PostgreSQL 16 and connects the backend through `DATABASE_URL`. `backend/migrations/` defines event, run, checkpoint, asset and W5 projection tables. `backend/internal/persistence/` implements schema migration, a per-run advisory writer lease, transactional event/projection writes, deduplication, frozen integrity status, ordered reads and restoration from the complete stored prefix. The twin publishes only after journal commit. Durable MQTT mode uses manual acknowledgments after commit, ignores events for unregistered runs instead of stopping, and exits non-zero if durable ingestion fails. The backend still cannot recover messages absent from PostgreSQL; a restored run is `uncertain` unless already frozen as `gap` or `conflict`.

Checkpoints store a SHA-256 fingerprint per accepted event rather than a full envelope copy; work-order projections are written only on order lifecycle events and terminal board exits instead of every PCB event. A checkpoint is verified in one ordered scan of the committed prefix: fingerprint index, sequence mapping, schema version, simulated-time monotonicity, event columns, trace entries and the persisted board/work-order projections must all agree before it is used. Mismatch, corruption or version drift falls back to full replay. Three checkpoints are retained per run.

`GET /api/runs/{id}/replay?simTimeMs=N` reconstructs the stored prefix up to and including the requested time without changing live state. `GET /api/runs/{id}/events?fromSimTimeMs=N&toSimTimeMs=N&afterSequence=N&limit=N` is a bounded ordered event query. The remote UI has a read-only simulated history view; the live WebSocket stays separate and current MES trace lookup is hidden while viewing history. See README for commands and security limitations.

`GET /api/metrics` provides process-local accepted, duplicate, conflict, gap and storage-error counters, last sequence per in-memory run, and current Go allocated heap bytes. Restored suffix events contribute to the accepted counter; counters reset on process restart and are not certified production metrics or peak RSS. The endpoint shares the same localhost-only, unauthenticated security boundary as the rest of this demo.

## Evidence so far

- A fresh isolated Compose project `w6-proof-20261109` produced and stored 3,411 events for 100 boards. Work order reported 100 completed, 98 passed, 2 failed; after a backend restart the same counts and 23-entry `board-1` trace were restored with a new epoch. Integrity remained `uncertain` as required by the missing-tail limitation. This is a manual test, not evidence for all crash or network interleavings.
- A separate 1000-board **100000x burst failed**. Simulator exited 0 after roughly 12 seconds, while PostgreSQL contained only sequences 1–11381; backend detected `expected sequence 11382, got 11385` and froze with `gap`. Mosquitto explicitly logged `Outgoing messages are being dropped` for the backend subscriber, consistent with its configured bounded 10,000-message/16 MiB queue. Broker PUBACK is not end-to-end delivery. The failed project's volume is retained for investigation.
- A fresh 20× paced 1000-board run (`w6-paced-20261109`, `compose.w6-load.yml`, seed 2026) reached 34,911 contiguous events and an order count of 1000 created/completed, 944 passed and 56 failed; distinct first-entry and final-exit board IDs were each 1000. The broker log contained no drop line. Integrity still read `uncertain`: counts alone cannot prove that no unobserved tail was missed. Ingestion spanned 377.79 s, approximately 92.41 events/s and 2.65 completed boards/s. Wall-time `ingestedAt - emittedAt` percentiles were p50 139.39 ms, p95 11,356.71 ms and p99 16,577.48 ms (same host clock; no negative samples). A single post-run backend memory sample was 59.95 MiB, not a peak. After restart, revision 34911, the reconciled order and 23-entry `board-1` trace were restored under a new epoch; readiness took tens of seconds because the full prefix is replayed. The slower run does not erase or negate the burst failure.
- Test environment for these local runs: Linux WSL2 6.18.54.1, Intel Core i7-8700K, 12 logical CPUs. A single Docker backend memory sample during the failed run was 14.93 MiB; this is neither a peak nor a complete benchmark. Separately, `node scripts/measure-performance.mjs` measured 18.82 requestAnimationFrame fps over 5.10 seconds in the **local** browser demo, headless Chromium 158, SwiftShader, 1366×768, DPR 1; backend restart/recovery was running at the same time. This is a software-rendered diagnostic, not a remote-view GPU benchmark or a target-hardware claim.
- The final timestamp of the paced 1000-board run was queried via the replay API and returned revision 34911, 1000 boards and completed order with `uncertain` integrity. An earlier inspection command expected the newly added `synthetic` response field from an older running image and failed; the repeated command checked the response actually available in that image. The current implementation adds `synthetic: true`.
- After checkpoints were implemented, a fresh 100-board Compose run stored six checkpoints through sequence 3000. Backend restart reconstructed revision 3411, the same completed order and counts, and the final historical API returned revision 3411 and 100 boards. PostgreSQL tests also exercise corrupt-checkpoint fallback and checkpoint/suffix selection. The earlier 1000-board timings were taken before checkpoints were added and are not a benchmark of the checkpoint implementation.
- A subsequent clean stop of that backend saved a seventh checkpoint at sequence 3411. Shutdown tests verify that a final checkpoint waits for consumer exit and is skipped if that wait times out. PostgreSQL subprocess tests force-killed a writer before starting append and after a committed append but before in-memory publication; recovery respectively observed zero and one event. A third test kills a subprocess after direct SQL inserts/updates inside an uncommitted transaction and verifies rollback; this exercises the database boundary but does not inject a kill inside the production append function. None of these covers every MQTT delivery interleaving.
- A second fresh 20× 1000-board run with periodic checkpoints enabled reached 34,911 contiguous events, 69 checkpoints and 1000 distinct first-entry and final-exit IDs, with 944 passed / 56 failed; no broker drop line was found. Ingestion spanned 391.93 s (89.07 events/s); same-host emission-to-ingestion percentiles were p50 169.60 ms, p95 24,955.43 ms and p99 30,595.73 ms. One post-run Docker memory sample was 64.79 MiB, not a peak. Integrity remained `uncertain`. These timings include other local development/test activity and do not establish an isolated performance baseline. A backend restart restored revision 34911 and reconciled order counts, but required roughly 50 seconds because the pre-fix checkpoint was rejected and full replay ran; the corrected measurement is in the next bullet. This run was started before the microsecond-normalization fix. Its final live snapshot and `replay?simTimeMs=7025000` response matched on revision, sequence, simulated time, machines, boards, work orders, source emission time and ingestion time.
- After the microsecond normalization and checkpoint repair were rebuilt, the same 1000-board database restart was measured again. With an incompatible pre-fix checkpoint the backend still fell back to full replay (58 s, accepted 34911). A clean stop then replaced that checkpoint with a verified, microsecond-precision copy; subsequent restarts were ready in 0–2 s with accepted 0 and revision 34911, and a `replay?simTimeMs=7025000` request completed in 1.28 s and matched the live snapshot on all compared fields. A graceful stop pruned checkpoint storage to the three most recent sequences (34000, 34500, 34911).
- After the review-driven fingerprint index and projection cross-check landed, a legacy checkpoint was again rejected once (60 s full replay); a clean stop rewrote it, and the next start was ready in 1 s with accepted 0 and revision 34911. The final historical query took 901 ms and again matched the live snapshot on revision, sequence, simulated time, machines, boards, orders and timestamps. Three checkpoint rows occupied 8.4 MB in total. Cross-checking legacy `board_trace` rows required a 1.5 µs tolerance because PostgreSQL stores microseconds while older rows retained nanoseconds; drift larger than 1 µs still falls back to the log, covered by two PostgreSQL tests.
- Backend memory after checkpoint-assisted restore was higher than the earlier full-replay observation: three consecutive historical queries reported 150, 223 and 208 MiB of Go heap, and one post-restore Docker sample was 329.8 MiB. The heap did not grow monotonically across those queries, so this appears to be GC sawtooth rather than an unbounded per-request leak, but it is not a peak measurement and no long-running soak test was performed.
- A PostgreSQL test compares checkpoint-assisted historical snapshots and PCB trace against full replay at simulated times 1, 2, 499, 500, 501 and 999. It exposed a nanosecond-versus-PostgreSQL-microsecond ingestion-time mismatch; durable ingestion now normalizes to microseconds before both projection and persistence. Checkpoint loading verifies stored trace ingestion times and falls back to the log on mismatch, including checkpoints produced before this correction. Checkpoint storage is bounded to the three most recent checkpoints per run; older derived rows are deleted while the event log is retained. A damaged checkpoint at the current cursor is replaced by a freshly derived copy on clean shutdown; invalid or incompatible checkpoints still fall back to full replay. Retention and repair are covered by PostgreSQL tests.
- `npm test`: 44 passed, 1 optional parity test skipped in the final default run. `npm run test:e2e`: one earlier run executed concurrently with the long historical query and Go race tests had four timeout failures (dashboard, simulation, remote switch and superseded remote trace); after the load stack was stopped and without parallel checks, that rerun and the final serial rerun each had 19 passed, 1 optional parity test skipped. Resource contention is a plausible explanation for the four timeouts, not a proven root cause. With the W4 fixture prepared separately, `W4_PARITY=1 npx vitest run tests/unit/twin-w3-parity.test.ts` passed 1 test, and `W4_PARITY=1 npx playwright test tests/e2e/remote.spec.ts` passed 3 tests. The final serial runs of `go test -race -count=1 ./...` and `go vet ./...` passed in both Go modules; the opt-in PostgreSQL and MQTT integration tests passed; lint, typecheck and build passed. Build still reports a 1,601.08 kB chunk warning. npm still reports 8 moderate and 2 critical advisories in existing dependencies.

## Review-driven hardening

After the first full review pass, the checkpoint index was reduced to per-event SHA-256 fingerprints, and checkpoint verification now scans the committed prefix once and cross-checks the event index, trace entries and persisted board/work-order projections. Work-order projections are written only on order lifecycle events and terminal board exits rather than every PCB event. A simulated-time regression is rejected in memory before persistence; unregistered-run MQTT traffic is discarded instead of stopping the consumer; durable ingestion failure exits non-zero; conflict metrics and database-unavailable replay `503` responses have tests; and the load script accepts a fresh run ID. A new integration test stops and restarts the broker while a durable consumer runs, then verifies resubscription, contiguous continued ingestion and retained `uncertain` status; it passed alongside the backend race suite, the PostgreSQL suite, lint, typecheck and unit tests.

Remaining limits are explicit: the consumer uses a clean session with a process-unique client ID, so QoS 1 messages unacknowledged at disconnect are not redelivered by the broker, and durable failure fails closed instead of retrying in-process. Replay accumulates the selected prefix in memory without a concurrency or byte cap. There is no automatic missing-event repair, and the remote history UI has no real-stack browser test. The documented Compose command starts a fixed run ID, so a second `up` with a new publisher freezes the stored run; use a backend-only restart or a fresh run ID.
